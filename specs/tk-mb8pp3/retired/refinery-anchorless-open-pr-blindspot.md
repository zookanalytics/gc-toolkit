**UPDATE 2026-07-22 — blind spot CLOSED by automation.** The pack shipped an anchorless-PR pass in `reconcile-merged-prs.sh` (live in rig checkout at #198 / `47e36fe`; runs every refinery idle wake as part of the find-work reconcile cadence). It enumerates `gh pr list --state open`, subtracts every PR named by a LIVE bead (fail-closed if the ledger read returns empty), resolves each remaining PR back to the CLOSED bead that opened it, and **escalates exactly once**: it stamps `metadata.anchorless_flagged=<pr#>` on the closed anchor **before** mailing mayor (stamp-first-mail-second), so the next pass sees the flag and only *reports* "already escalated, awaiting operator disposition" — no re-mail, safe at the 60s cadence. Verified live 2026-07-22: it flagged all 7 (tk-3s5uo=171, tk-6d0vb.1.4=170, tk-ae96t.2=166, tk-ghut9=108, tk-7druqk=88, tk-9obwui=80, tk-kcr8v6=77), the immediate next pass reported "0 escalated". **So: a refinery no longer needs the manual `gh pr list` vs anchor cross-check below — the idle loop surfaces + bounds anchorless PRs automatically.** GOTCHA: the refinery *worktree* copy of the script can lag main (worktree was at e370eb9 while the rig checkout was at #198); the formula resolves SCRIPTS_DIR from `$GC_RIG_ROOT` (rig checkout) first, so the idle loop runs the current script even when the worktree is stale — don't judge script behavior from the worktree copy. The historical detail below is retained for context.

**UPDATE 2026-07-28 — the anchorless pass has THREE arms; the third is a benign false-positive surface.** Arm 1 = PR resolves to a CLOSED bead, not yet flagged → stamp `anchorless_flagged` + mail mayor once. Arm 2 = same, already flagged → report "already escalated, awaiting operator disposition" (the steady-state reading; suppress it in any idle-loop notification filter). Arm 3 = **"no bead in any state references it; not tracked by any automated path"** → the script `continue`s IMMEDIATELY: no stamp, no mail, log line only, by design ("there is nothing durable to mark, and an unbounded mail would repeat every wake"). **Because arm 3 needs the ledger lookup to come back EMPTY, a transient Dolt/bead-read hiccup makes a perfectly healthy anchor look untracked.** Seen live 2026-07-28: the idle loop reported PR#222 as anchorless while its anchor `tk-fn53m` was open and intact the whole time (`pr_number=222`, `merge_result=pull_request`, `check.codex=green@ebbfb928`); a direct `--metadata-field pr_number=222` query found it instantly and an observer re-run reported the normal "4 anchorless, 10 skipped" with #222 back among the tracked. **How to apply:** on an arm-3 line, do NOT escalate or hand-repair the bead. Re-run `reconcile-merged-prs.sh` standalone and re-query the anchor — it is safe to run alone because it is explicitly DETECT-ONLY (no merge authority, never calls `gh pr merge`), unlike `merge-skill.sh`, which must not be hand-run while an idle-loop driver is armed or two passes can race the same anchor. Only treat arm 3 as real if it repeats across passes AND the bead query independently comes back empty. Anchorless set on this date was 4 (#166, #88, #80, #77), down from the historical 7 below.

Both landing/reconcile scripts enumerate **by bead** (open beads with `merge_result=pull_request`). An open PR with **no such anchor bead** is in a blind spot — neither merge-skill (land) nor reconcile-merged-prs (close/escalate) can see it.

Seen 2026-07-02: 10 open PRs, only 3 (#179/#180/#184) had anchors. The other 7 (#77,#80,#88,#108,#166,#170,#171) had **CLOSED** beads (weeks old, 05-29→06-24), all `merge_result=pull_request` (NOT `=merged`) — i.e. closed under the OLD **close-on-publish** model (the bead's terminal state was PR-publication), PR left open for a separate merge that never came. Orphaned by the close-on-publish → close-on-land ([[refinery-close-on-land-model]]) transition. `merge_result=pull_request` on a *closed* bead (vs `=merged`) confirms no false "landed" claim — a stale open PR, not a data-integrity bug. **Boundary test:** close-on-land landed **2026-06-28** (PR #163, commit 40ea2d7). A stranded anchorless PR whose bead `closed_at` predates that is a known historical strand (harmless); one closed *after* would be a live close-on-land leak worth investigating.

**How to apply:** during a merge-queue check, cross-check `gh pr list --state open` against the anchor set (`gc bd list --status=open --metadata-field merge_result=pull_request`). Anchorless open PRs are NOT active refinery work (their beads are closed) — do NOT unilaterally merge or close them (outward-facing; needs judgment — several were Design-eval/Decide beads whose real output was bead notes, so their PR is vestigial). **Surface to the operator/mayor for a merge / close / leave decision.** Related: [[refinery-orphan-scan-unrouted]].

This is the key non-escalation signal: the blind spot only *loses* work when a **mergeable** anchorless PR rots — here every one is already gated behind human approval or needs a rebase, so there's no silent-merge risk and no recoverable-merge loss. Do NOT re-mail this each patrol; it's operator-visible in `gh pr list`, weeks-stable, and largely vestigial. Only escalate afresh if the set *changes* — e.g. a newly-anchorless PR appears that is `CLEAN`/`MERGEABLE` (real loss) — or the operator asks for a cleanup sweep.
