| 1 | [r4057442090](https://github.com/zookanalytics/gc-toolkit/pull/793#discussion_r4057442090) — part 3 | Human approval is recorded with the commit, but a rebase after approval is fine to ship absent major changes; a considered alternative was an agent judging whether changes warrant a re-review. | **Fixed** in part 3. | 3 | [r4057454768](https://github.com/zookanalytics/gc-toolkit/pull/793#discussion_r4057454768) — part 4 | PR-to-board links would help; action links in PR comments (for example, opening a visit for the PR) would be very useful; would have to settle which URLs to include. | **Fixed** in part 4. | 4 | [r4057459294](https://github.com/zookanalytics/gc-toolkit/pull/793#discussion_r4057459294) — tk-6ttx19 boundary | Is it true nothing resets `CHANGES_REQUESTED` into a review-again state in GitHub? If you ask the same person to review again, won't it reset? | **Answered; claim tightened.** Your suspicion holds. Re-requesting the same reviewer does not clear the All-PRs list status — the reviewer returns to "awaiting review" but the list still reads "changes requested" (documented, long-standing GitHub behavior; community discussion [#17875](https://github.com/orgs/community/discussions/17875)). Pushing a fix does not clear it either. The one native reset is dismissing the review through the dismissals API, which erases the reviewer's recorded verdict and, under required review, drops the PR back to "review required." The section now states this and frames a label as the additive alternative that preserves the verdict; the dismiss-versus-label tradeoff is tk-6ttx19's to settle. |

Draft no longer competes with the status representation, which is the separation the comment asked for. |
